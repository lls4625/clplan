# 日历首帧无滚动定位优化

## 需求与范围

- App 从欢迎页进入日历主页时，第一帧就应已经定位到当前日期。
- 消除先显示年初，再急速跳到当前日期的视觉过程。
- 仅调整月份日历视图的首次滚动位置初始化。

## Flutter 官方实现基线

- `ScrollController.initialScrollOffset`：<https://api.flutter.dev/flutter/widgets/ScrollController/initialScrollOffset.html>
- `ScrollController`：<https://api.flutter.dev/flutter/widgets/ScrollController-class.html>
- `ScrollView.controller`：<https://api.flutter.dev/flutter/widgets/ScrollView/controller.html>
- `ScrollController.createScrollPosition`：<https://api.flutter.dev/flutter/widgets/ScrollController/createScrollPosition.html>

Flutter 官方明确支持通过 `ScrollController.initialScrollOffset` 控制 ScrollView 的初始滚动位置。该值会在 `ScrollPosition` 创建时作为 `initialPixels` 传入，因此目标位置可以直接参与首次布局，不需要等待首帧绘制完成后再调用 `jumpTo`。

## 修改前

- 日历滚动控制器的初始 offset 为 `0`。
- 首次布局因此从 1 月附近开始。
- 首帧绘制完成后，再计算今日的 offset 并调用 `jumpTo`。
- `jumpTo` 虽然没有动画时长，但因为年初内容已经完成一帧绘制，用户仍会看到一次短暂而快速的位置变化。

## 修改后

- `_CalendarScrollController` 支持传入 `initialScrollOffset`。
- `CalendarPageState.initState` 先根据当前日期、月标题高度、月底间距、每月周数和当前日历行高，计算今日所在行的绝对 offset。
- 创建滚动控制器时将该 offset 作为 `initialScrollOffset`。
- 移除首帧绘制后的 `jumpTo`。
- 日历首次布局就从今日所在行开始，不再先绘制年初位置。

## 修改内容与原因

### `lib/calendar_page.dart`

1. 为 `_CalendarScrollController` 增加 `initialScrollOffset` 构造参数，并传递给 Flutter 官方 `ScrollController`。
2. 将 `scroll` 改为在 `initState` 内创建，确保创建前已读取用户的日历行高偏好。
3. 拆出 `_monthRowOffsetForDate`，用于计算不依赖 viewport 的日期行绝对 offset。
4. 原有 `_monthOffsetForDate` 复用新方法，继续为“回到当前日期”及视图切换保留带 viewport alignment 的计算。

原因：首帧绘制之前还没有 `viewportDimension`，无法在不进行二次位置修正的前提下精确保留原来的 `alignment: .2`。本次优先保证“第一帧已定位且无任何可见移动”，因此将今日所在行作为初始可见区域的起点。

## 可能影响与注意事项

- 首次进入日历时，今日所在行将靠近日历滚动区域顶部，不再是首帧后校正到视口约 20% 的位置。
- 年末时，Flutter 的滚动布局会将超过最大范围的初始位置校正到有效边界，今日仍会保持可见。
- 用户之后点击“回到当前日期”时，仍使用原有 alignment 逻辑。
- 日历行高偏好在创建控制器前已加载，初始 offset 会按当前行高计算。
- 本次未修改周卡片视图、计划卡片或日历日详情卡片。
- 工作区中原有 `lib/stats_page.dart` 修改与本次无关，本次未触碰该文件。

## 双指缩放与关联功能影响复核

### 月份视图双指缩放

- 缩放开始时仍从 `scroll.offset + focalY` 记录手指焦点对应的文档坐标。
- 行高改变时，`_mapDocumentYForRowHeight` 仍使用当前 offset 映射新日历高度，再通过 `correctToOnNextDimensions` 在新布局尺寸中修正位置。
- `initialScrollOffset` 仅决定第一个 `ScrollPosition` 的初始 `pixels`，不会参与后续的焦点计算、行高映射或 `pendingPixels` 修正。
- 结论：不会改变现有的双指缩放中心锚点和单指接管滚动逻辑。

### 周卡片视图双指缩放

- 周卡片视图继续使用同一个已创建的 `ScrollController` 和 `ScrollPosition`。
- 周卡片高度改变时仍由 `_mapWeeklyDocumentYForCardHeight` 和 `correctToOnNextDimensions` 保持缩放焦点。
- 结论：首次初始 offset 不会在周卡片缩放时重新应用。

### 月份/周卡片视图切换

- 切换视图时没有创建新的 `CalendarPageState` 或新的 `_CalendarScrollController`。
- Flutter 在因组件重建需要新 `ScrollPosition` 时会传入 `oldPosition`；当前自定义 `_CalendarScrollPosition` 会由父类吸收旧位置，已有 pixels 优先于 `initialPixels`。
- 切回月份视图时，现有 `pendingPixels` 仍会在新尺寸生效后定位到今天。
- 结论：不会因 `initialScrollOffset` 而在每次切换时重置到初始位置。

### 回到今天、月份跳转和普通滚动

- `goToToday`、`_scrollToMonth`、`_revealWeek` 和 `_revealKey` 都在 ScrollView 已创建后操作当前 `ScrollPosition`，不读取 `initialScrollOffset`。
- 普通滚动、惯性滚动、缩放期间的用户滚动锁定和缩放结束后的解锁均保持原实现。
- 结论：无额外行为变化。

### 复核总结

静态调用链复核未发现需要进一步修改的冲突。本次变更只将“首帧后设置 pixels”改为“创建首个 `ScrollPosition` 时设置 pixels”；双指缩放及其他交互仍基于运行期的 `scroll.offset`、新尺寸和焦点进行计算。

## 按操作时序的深入排查

### 1. 欢迎页进入日历

1. `WelcomePage` 取消倒计时并将 child 切换为 `HomeShell`。
2. `CalendarPageState.initState` 读取已加载的行高偏好。
3. 根据当前年、月、日和行高计算今日所在行的文档 offset。
4. `_CalendarScrollController` 将该值传给首个 `_CalendarScrollPosition.initialPixels`。
5. Sliver 第一次布局时直接创建当前日期附近的子项。

此路径没有 post-frame 位置变更，也没有调用缩放用的 `pendingPixels`。

### 2. 首次单指滚动

- 首帧结束后，`ScrollPosition.pixels` 就是已经布局确认的当前 offset。
- 单指滚动继续进入 `_CalendarScrollPosition.applyUserOffset`。
- `_userScrollLocked` 初始为 `false`，因此首次滚动不会被新的初始定位逻辑阻止。

### 3. 月份视图双指缩放

1. 第二个指针按下时锁定普通滚动。
2. 以当前 `scroll.offset + focalY` 记录焦点文档坐标。
3. 行高变化时，用旧高度到新高度的月份/周行映射计算新 offset。
4. 将新 offset 写入 `pendingPixels`，并在新尺寸生效时由 `correctForNewDimensions` 修正。
5. 松开一指后，剩余指针可继续通过 `applyHandoffUserOffset` 滚动。
6. 所有指针离开后解锁普通滚动并异步保存行高。

`initialScrollOffset` 只在上述步骤之前的首个 `ScrollPosition` 创建时生效，不会进入任何一步缩放计算。

### 4. 周卡片切换与缩放

- 月视图切换到周卡片时，复用同一个 controller，然后由 `_revealCurrentWeek` 定位当前周。
- 周卡片缩放使用独立的卡片高度、周高度和焦点映射，不使用月视图的初始 offset 公式。
- 切回月视图前，目标位置写入 `pendingPixels`；新尺寸生效后优先由 `correctForNewDimensions` 使用该值。
- 若 Flutter 创建新 `ScrollPosition`，`oldPosition` 会先被吸收；已有 pixels 不会被 `initialPixels` 覆盖。

### 5. 高度保存与 `AnimatedBuilder` 重建

- 月视图和周卡片缩放结束后会异步保存高度，然后 `AppController.notifyListeners()`。
- `HomeShell` 会重建，但 `CalendarPage` 使用稳定的 `calendarKey`，`CalendarPageState` 和已创建的 controller 会保留。
- 因为不会再次执行 `initState`，`initialScrollOffset` 不会因保存完成后的重建而重新应用。

### 6. 前后台和页签切换

- `IndexedStack` 保留日历页，切换到计划、统计或设置页不会销毁 `CalendarPageState`。
- App 回到前台时的通知刷新可能触发重建，但不会重建 controller 或重置滚动位置。

## 深入排查发现的既有边缘风险

以下问题在本次 `initialScrollOffset` 修改前已经存在，不是本次修改引入；本次未自行扩大范围修复。

1. **连续快速缩放的异步保存竞态**
   - 每次缩放结束都会异步写入数据库。
   - 若前一次保存晚于后一次返回，旧高度可能短暂覆盖新高度，或成为最终持久值。
2. **跨日/跨年恢复时的当前日期状态**
   - App 长时间留在后台并跨过零点或新年后，前台恢复只刷新通知。
   - `CalendarPageState.year`、`jumpMonth` 和已选日期不会自动切换到新的“今天”，需要用户点击“回到当前日期”。
3. **设置页直接改变日历行高时的锚点**
   - 设置页更新行高后，日历 `build` 直接更换 `rowHeight`。
   - 该路径没有像双指缩放一样执行文档坐标映射和 `pendingPixels` 修正，因此返回日历时可能看到逻辑日期位置改变。
   - 后续状态：设置页行高入口已删除，该风险已消除。见 `docs/vibe/2026-10-23_13-32-42-移除日历行高设置与风险重评.md`。
4. **激活缩放期间切换视图的非常规多指场景**
   - 日历区域保持两个指针时，若用第三指点击顶部视图切换按钮，当前实现没有在切换前显式取消旧视图的指针集合和缩放会话。
   - 该场景可能导致短暂的滚动锁定或状态残留，与首屏定位改动无关。

## 验证说明

按项目协作约束，本次未执行构建、编译、打包、静态分析、格式化或任何自动化测试。

建议手动验证：

- 等待欢迎页自动进入日历主页，确认第一个可见的日历画面已是当前日期附近。
- 点击“开始规划”提前进入，确认同样没有年初到今天的短暂位移。
- 切换小、中、大日历行高后分别冷启动，确认当前日期行可见。
- 首次进入后立即进行月视图双指放大和缩小，确认手指中心下的日期保持稳定。
- 双指缩放后松开一指，使用剩余指针继续上下滚动，确认没有锁死或跳位。
- 切换到周卡片视图后双指缩放，再切回月视图，确认缩放锚点、当前周和当前日期定位正常。
- 验证“回到当前日期”、月份下拉和月份/周卡片切换仍保持原有行为。
