# 移除日历行高设置与风险重评

## 需求与范围

1. 删除设置页中的日历行高/间距设置，App 仅通过日历页双指缩放更新并记录高度。
2. 在删除设置入口后，从操作逻辑重新评估首屏定位、双指缩放、持久化、视图切换与前后台恢复风险。
3. 本次只实施第 1 项；第 2 项输出风险结论和优化方案，不未经确认扩大代码修改范围。

## Flutter 官方实现基线

- `ListView`：<https://api.flutter.dev/flutter/widgets/ListView-class.html>
- `TextEditingController`：<https://api.flutter.dev/flutter/widgets/TextEditingController-class.html>
- `ScrollController.initialScrollOffset`：<https://api.flutter.dev/flutter/widgets/ScrollController/initialScrollOffset.html>
- `ScrollController.createScrollPosition`：<https://api.flutter.dev/flutter/widgets/ScrollController/createScrollPosition.html>
- `WidgetsBinding.addPostFrameCallback`：<https://api.flutter.dev/flutter/widgets/WidgetsBinding/addPostFrameCallback.html>

设置页仍使用 Flutter 官方 `ListView` 组织其他设置项。日历行高编辑器被整体移除后，对应 `TextEditingController` 及其生命周期也一并删除，不留下脱离 UI 的控制器对象。

## 修改前

- 设置主页“显示与通知”分组中有“日历显示”入口。
- 详情页可手工编辑小、中、大三个日历密度档位的日期格高度。
- 手工保存与月视图双指缩放共用 `saveCalendarDensityHeights`。
- 设置页修改行高时，日历页会在 `build` 中直接更换 `rowHeight`，没有经过双指缩放的锚点映射。

## 修改后

- 设置主页不再显示“日历显示”。
- `_calendarDetail`、`_CalendarDensityEditor`、三个文本控制器、数值验证、帮助文案和手工保存逻辑已删除。
- 月视图双指缩放结束后仍调用 `saveCalendarDensityHeights`，只更新当前历史密度档位对应的行高。
- 周卡片双指缩放结束后仍调用 `saveCalendarWeeklyCardHeight`。
- 旧的数据库字段、默认值和偏好读取逻辑保留，避免破坏已有用户数据或引入额外迁移。

## 修改内容与原因

### `lib/settings_page.dart`

- 删除“日历显示”菜单项。
- 删除 `_calendarDetail`。
- 删除 `_CalendarDensityEditor` 及全部状态、输入、验证和保存逻辑。

原因：将日历高度的用户操作入口统一为日历页双指缩放，避免设置页与直接手势同时维护两套高度调整路径。

### 有意保留的数据与方法

- `AppPreferences.calendarDensity`
- `calendarSmallHeight` / `calendarMediumHeight` / `calendarLargeHeight`
- `AppController.saveCalendarDensityHeights`
- `AppDatabase.getPreferences` 中的兼容读取

原因：当前双指缩放仍使用这些字段保存月视图高度。直接删除会扩大为偏好模型和数据迁移改造，不属于本次“删除设置页入口”的必要范围。

## 调整后的风险重新评估

### 已消除：设置页改行高导致锚点漂移

手工设置入口已删除，运行中行高变更只能由日历双指缩放触发。该路径会通过 `_mapDocumentYForRowHeight` 和 `correctToOnNextDimensions` 保持手指焦点，因此原评估中的“设置页返回后逻辑日期跳变”风险不再存在。

### 低风险：首屏初始定位与双指缩放

- `initialScrollOffset` 只在首个 `ScrollPosition` 创建时设置初始 pixels。
- 用户可开始操作时，布局已完成，缩放按当前 `scroll.offset` 记录焦点。
- 缩放新尺寸仍由 `pendingPixels` 和 `correctForNewDimensions` 修正。
- controller 在 `CalendarPageState` 中保持，保存高度触发的重建不会重新应用初始 offset。

结论：未发现本次两项调整对双指缩放引入新冲突。

### 中风险：连续快速缩放的异步持久化

月视图缩放每次结束都会无等待地启动 `_saveScaledRowHeight`，内部顺序写入三个偏好键。周卡片也会无等待地启动独立写入。若用户在前一次写入完成前再次缩放，会存在多个未等待 Future：

- 写入时序依赖底层数据库调度。
- 旧请求完成后的 `preferences.copyWith` 可能短暂将内存偏好恢复为旧值。
- 新的 controller 通知会导致 `HomeShell` 和日历重建，增加快速连续操作时的时序复杂度。

### 中低风险：激活缩放时切换月/周视图

常规两指操作时无法同时点击顶部按钮，但多指或辅助输入仍可能在 `pinchSessionActive` 为 `true` 时触发 `toggleCalendarView`。当前切换前不会清理指针集合或解锁 scroll，可能造成短暂状态残留。

### 中低风险：跨日/跨年恢复

App 回到前台时只刷新通知数据，不刷新 `CalendarPageState.year`、`jumpMonth`、`visibleMonth` 和 `HomeShell.selectedDate`。若应用跨过零点或新年，“今天”标记会按 `DateTime.now()` 重建，但选中日期和年/月状态可能仍是旧值。

## 建议优化方案

### 优先级 P0：将缩放高度持久化改为“最新值胜出”

建议将月视图与周卡片的高度保存收口到 `AppController`，使用每类高度独立的串行写入队列和版本号：

1. 手势结束时立即更新页面内存高度，不阻塞 UI。
2. 将待保存值覆盖为最新值，不为每次快速缩放累积一个完整写入任务。
3. 同一时刻每类高度最多只有一个数据库写入在执行。
4. 当写入完成时，若版本号已过期，不用旧值覆盖 `preferences`，继续写入最新待保存值。
5. 只在最新值确认后对外通知，避免过期值触发日历重建。

月视图可进一步新增单值方法，例如 `saveCurrentCalendarRowHeight(double height)`，由 controller 根据当前兼容档位更新对应字段，避免页面每次携带三个高度快照。

### 优先级 P1：缩放活动期间禁止切换视图

- 向 `CalendarPageState` 增加只读缩放活动状态，或让 `toggleCalendarView` 在 `pinchSessionActive` 时直接返回。
- 更完整的做法是在视图切换前统一调用会话清理方法，清空月/周指针集合、取消未处理缩放帧、解锁 scroll，再进行切换。
- 建议优先采用“活动期间不响应切换”，改动小且不会中断当前手势。

### 优先级 P1：明确跨日恢复策略

建议保存最后一次已知的“今天”，App 恢复时比较日期：

- 无论用户当前浏览位置如何，都重建日期标记，使新的今天高亮正确。
- 只有当用户在进入后又未主动离开旧的今天时，才自动跟随到新的今天。
- 若用户正在浏览历史或未来日期，保留其滚动位置，避免恢复 App 时无条件打断用户上下文。

该策略涉及产品行为选择，实施前应获得用户确认。

### 优先级 P2：将三档历史字段收敛为单一行高

设置页已不再提供密度档位选择，长期看可将月视图高度收敛为单一 `calendar_row_height` 偏好：

1. 读取新字段；缺失时按现有 `calendarDensity` 从三档历史值中迁移。
2. 双指缩放只写入新单值字段。
3. 保留旧字段读取一个兼容周期，后续再考虑清理。

这是数据模型迁移，影响范围明显大于本次 UI 删除，不建议与当前修复合并实施。

## 可能影响与注意事项

- 用户将不再能通过数字输入精确设置日历行高。
- 月视图和周卡片的高度范围限制仍保留在手势处理和 controller 中。
- 已保存的行高不会因删除设置 UI 而丢失。
- 设置页不再含有日历行高说明；如需向用户提示双指缩放，应在日历页的帮助或首次操作提示中单独设计，不应重新引入手动高度输入。
- 工作区中原有 `lib/stats_page.dart` 修改与本次无关，本次未触碰。

- 设置页“显示与通知”中已无“日历显示”入口。
- 月视图双指缩放后退出并重启 App，行高保持。
- 周卡片视图双指缩放后退出并重启 App，卡片高度保持。
